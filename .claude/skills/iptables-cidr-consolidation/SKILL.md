# iptables CIDR 統合

## このスキルの目的

手作業で管理している iptables のブロックリストは、1 つずつ IP を追加していくうちに
肥大化する。数か月もすれば、同じネットワークに属するエントリや、リストの別の場所に
ある「より広い CIDR ルール」で既にカバーされている個別 IP が溜まっていく。複数の
サーバで似たブロックリストを別々に育てていると、サーバ間で同じ IP が重複していく。
このスキルはそうした統合の機会を見つけ出し、カバー範囲を失わずにリストを縮める。
さらに範囲を広げる前に RDAP で *実際に* 割り当てられたブロックを確認するので、1 台の
悪質ホストをうっかりクラウドプロバイダ全体のブロックに変えてしまうことがない。

目標は **より短く、かつ同じだけ安全な** リスト。簡潔さのために正確さを犠牲にしては
いけない。ルールを広げる価値があるのは、その広いブロックが本当に敵対的である、または
単一のアクター専用である場合だけ。

## 入力

典型的には `iptables -L`（または `iptables -L -n`）の出力で、次のような形をしている：

```
target     prot opt source               destination
REJECT     all  --  20.9.77.23           0.0.0.0/0            reject-with icmp-port-unreachable
REJECT     all  --  104.234.0.0/16       0.0.0.0/0            reject-with icmp-port-unreachable
```

`source` 列をパースする（行内の最初の IP トークン。`0.0.0.0/0` は destination なので
除外する）。どのエントリが単一 IP で、どれが既に CIDR なのかを区別しておくこと —
どちらも後の手順で重要になる。ファイルが単なる IP の一覧であることもあるので、その
形式にも対応する。

**複数サーバの場合**：各サーバのルールを抜き出したファイルが複数あり、ファイル名が
サーバ名になっていることが多い。すべてをまとめて 1 つの共有 CIDR ブロックリストに
したい、というのが典型的な依頼。まず全ファイルをマージしてユニーク化する（手順 0）。

## 同梱スクリプト

標準ライブラリのみで動く。`scripts/` 配下。

- **`rdap_lookup.py`** — IP/CIDR の登録ブロックを RDAP で引く（手順 3）。レート制限・
  接続リセットを吸収し、`whois` 不要。出力は `IP<TAB>allocated_cidr<TAB>org`。
- **`consolidate.py`** — マージ・冗長検出・/24 バケット・登録ブロック集計・包含検証・
  最終リスト生成といった機械的処理を一手に引き受ける。手作業で ipaddress を書き直す
  より速く、取りこぼしがない。サブコマンド：

  ```bash
  # 手順0-2: 複数ファイルをマージし、冗長/24バケット/サーバ間重複を一括レポート
  python scripts/consolidate.py analyze ubuntu.txt web1.txt --dump-ips ips.txt
  # 手順5: 登録ブロックに個別IPがN件以上入っているもの（ホットブロック）
  python scripts/consolidate.py hotblocks --rdap rdap.tsv --min 5 ubuntu.txt web1.txt
  # 手順6: 適用するCIDRが実際にどの単一IPを覆うか検証（タイル化登録の罠を防ぐ）
  python scripts/consolidate.py check --cidr 20.192.0.0/10 --cidr 34.32.0.0/11 ubuntu.txt web1.txt
  # 手順8: 最終マージリスト（素の一覧）を生成。--add のCIDRに包含される単一IPは自動削除
  python scripts/consolidate.py build ubuntu.txt web1.txt --add 195.178.110.0/24,20.192.0.0/10 -o merged-blocklist.txt
  ```

  入出力は UTF-8 を強制し、cp932 などで保存されたファイルも読めるようにしている
  （Windows での文字化け対策。後述の注記参照）。

## ワークフロー

### 0. 複数サーバならまずマージする

複数ファイルが渡されたら、全部の `source` を 1 つのユニークな集合にまとめる。ここで
得られる素の効果が大きい：別々のサーバに散らばっていた同一 IP・同一 CIDR が 1 行に
畳まれる。`consolidate.py analyze FILES...` はこのマージを行い、サーバ間で重複していた
単一 IP も一覧する。以降の手順は、このマージ済み集合に対して行う。単一ファイルなら
この手順は素通りでよい。

### 1. 既存の CIDR で既にカバーされているエントリを見つける（純粋な冗長）

凝ったことをする前に、まず *リストに既にある* CIDR の内側に入る単一 IP を探す。これ
らは死荷重 — より広いルールが既にブロックしている — ので、挙動を一切変えずに削除
できる。最も確信度が高く、最もリスクの低いクリーンアップなので、最初に、かつ独立した
セクションとして提示する。マージ後はこれが効くことが多い（例：あるサーバの単一 IP が、
別サーバが持っていた `/24` に内包される）。

例：`185.177.72.0/24` がリストにあるなら、`185.177.72.38`・`185.177.72.52`・
`185.177.72.70` はすべて冗長。`consolidate.py analyze` が「手順1」として列挙する。

### 2. 残った単一 IP を /24 ごとにまとめて統合候補を見つける

個別 IP を先頭 3 オクテットでバケットに分ける。2 つ以上の IP が入っているバケットは、
1 つのルールにまとめる候補 — 同じ /24 から複数回ヒットしているなら、たいていそのサブ
ネット全体が敵対的だ。範囲をできるだけ狭く広げたい場合は、隣接する IP（例：`.153` と
`.154` → 狭い `/30`）にも注目する。`consolidate.py analyze` が「手順2」として出す。

ここではまだ CIDR を確定しない — 手順 3 で何が実在するかを確認する。

### 3. RDAP で実際に割り当てられた CIDR を確認する

ここが肝心な手順。RDAP（`whois` の現代的で構造化された後継）を引く目的は、ある IP が
属する *登録された割り当て* を知ること。これにより次の違いを見分けられる：

- 1 台の防弾/VPS ホスト専用の狭い `/24`（丸ごとブロックしても安全）と、
- Microsoft Azure に属する `/11`（ブロックすれば正規クラウドの巨大な一部を吹き飛ばす）。

`analyze --dump-ips ips.txt` で書き出したユニーク単一 IP（＋ユーザーが特定したいその他の
IP）を渡す。結果はファイルに保存しておくと、手順 5 の `hotblocks` で再利用できる：

```bash
python scripts/rdap_lookup.py --file ips.txt > rdap.tsv
```

スクリプトはまず高速な並行パスを行い、その後失敗分をバックオフ付きで逐次リトライ
する — バッチ全体を再実行するのではなく、時間を与えること。一部の IP（例：Azure の
ブラジル割り当て）は rdap.org が `406` を返すことがある。その場合は所管 RIR へ直接
（`https://rdap.lacnic.net/rdap/ip/<ip>` 等）、`Accept: application/rdap+json` を付けて
引き直すと取れることが多い。

### 4. 各結果を「広げてどれだけ安全か」で分類する

結果を 3 つのティアに分ける。ティアを決めるのは **割り当てブロックのサイズ** と
**所有者が誰か** — まさに RDAP が教えてくれた情報だ。

- **統合して安全** — 複数の掲載 IP が、ホスティング/VPS/防弾プロバイダ所有の *同じ
  登録済みの小さなブロック*（おおよそ /22 以下）に収まる。個別 IP をそのブロックで
  置き換える。最も強いケースは、登録がちょうど `/24` で、リスト内の複数 IP がそこに
  収まっている場合。

- **ポリシー判断（専用 /24 内の単一 IP）** — 掲載 IP は 1 つだけだが、それが乱用で
  知られるホスティングプロバイダの小さな専用 `/24` に収まっている。これは重複排除では
  なく、*先回り* の範囲拡大であり、ユーザーが望むかどうかは分からない。押し付けず、
  提案にとどめる。

- **広げない（ハイパースケーラ / 大規模割り当て）** — 割り当てが巨大なクラウド
  ブロック（Microsoft/MSFT、Google/GOOGL/GOOGLE-CLOUD、Oracle、DigitalOcean、
  Amazon/AWS、Tencent/ACEVILLE、Alibaba、…）で、しばしば /16 以下。既定では個別 IP の
  ままにする。広げると、クラウドを共有する正規のテナントをブロックしてしまう。掲載 IP
  が複数そのブロックを共有していても、ユーザーが巻き添えを明示的に受け入れない限り
  個別のままにする。**ただしユーザーが「Azure/GCP は制限してよい」と明示したら**、
  その巻き添えを受け入れたうえで統合提案に回す（手順 5・6 へ）。

便利な目安：登録ブロックが `/24` より長ければほぼ確実に専用ホスト（拡大を検討）、
`/16` 以下ならほぼ確実にクラウドか大手 ISP（既定では触らない）。`/23`〜`/19` の中間は
判断が分かれる — その旨を明記すること。

### 5. ホットブロックの洗い出し（登録ブロックに N 件以上）

「どの登録ブロックに個別 IP が固まっているか」は、統合の費用対効果を測る強い指標。
特にユーザーがハイパースケーラの制限に踏み切る場合、「5 件以上ヒットしている登録
ブロックだけ畳む」といった閾値で判断したいことが多い。

```bash
python scripts/consolidate.py hotblocks --rdap rdap.tsv --min 5 ubuntu.txt web1.txt
```

各ホットブロックについて、登録ブロック文字列・**全該当 IP を覆う最小 CIDR**・ハイパー
スケーラ判定・該当 IP 一覧を出す。閾値 `--min` はユーザーの要望に合わせる。

### 6. 適用する CIDR の包含を必ず検証する（重要）

**ここを飛ばさない。** RDAP は登録範囲を *複数の CIDR に分割（タイル化）* して返すこと
がある（例：`20.33.0.0/16, …, 20.64.0.0/10, 20.128.0.0/16`）。このとき「一番大きな構成
ブロック」を選んでも、対象 IP の大半はその *下位* に位置していて覆えない、という罠が
ある。実際、`20.64.0.0/10` を選んだのに該当 6 件のうち 1 件しか覆わない、`34.32.0.0/11`
で 7 件中 4 件しか覆わない、というズレが起きる。

適用候補の CIDR は、確定前に必ず包含を検証する：

```bash
python scripts/consolidate.py check --cidr 20.64.0.0/10 --cidr 34.32.0.0/11 ubuntu.txt web1.txt
```

グループ全体を 1 本で確実に覆いたいなら、`hotblocks` が出す「全該当 IP を覆う最小
CIDR」を使う（ただしこれは登録範囲より広く取りがちなので、巻き添えサイズを必ず併記）。
狭く抑えたいなら登録の構成ブロックを複数本に分ける。どちらもサイズと所有者を添えて
ユーザーに選ばせる — 黙って広い方を選ばない。

### 7. レポート

ティアごとに、最も実行可能なものから順にまとめる。提案する各 CIDR について、それが
どの現行エントリを置き換えるかを列挙し、ユーザーが妥当性を確認できるよう RDAP の
所有組織名を併記する。正味の効果を具体的に示す。例：「これら 8 エントリが 3 つに
まとまる」「2 サーバ計 135 行 → 113 エントリ」。冗長な削除（手順 1）は、ユーザーが
既に削除予定かもしれないので独立したセクションに残す。

ユーザーが RDAP の結果を保存したいと言った場合、ティアごと（さらに「広げない」ティア
内ではプロバイダごと）にグループ化した `IP → allocated_cidr (org)` の一覧が Markdown
で読みやすい。日付と、RDAP が返すのは登録単位であり運用上のサブネット境界と必ずしも
一致しないことを注記する。

### 8. 適用（依頼されたときのみ）

稼働中のルールセットやファイルを無断で編集しない — まずスコープを確認する。素の
マージリストを作るなら `consolidate.py build`：追加する CIDR を `--add` で渡すと、それに
包含される単一 IP（手順 1 の冗長分も含む）が自動で削除され、ソート済みの一覧が出る。

```bash
python scripts/consolidate.py build ubuntu.txt web1.txt --add 195.178.110.0/24,20.192.0.0/10 -o merged-blocklist.txt
```

出力形式はユーザーに尋ねる：素の IP/CIDR 一覧か、`iptables -L` 表示形式か、
`iptables-restore`（`-A INPUT -s <cidr> -j REJECT`）か、`ipset`（`ipset add <set> <cidr>`）か。

## 注記

- RDAP が返すのは RIR の *登録* ブロックであり、必ずしも運用上のサブネットではない —
  境界を過信しないよう、その旨を明示すること。
- 黙って範囲を広げてはいけない。すべての統合は、証明可能な冗長エントリを削除するか、
  あるいは影響範囲（所有者 + ブロックサイズ）とともにユーザーへ提示すること。
- タイル化された登録に対し「最大構成ブロック」を鵜呑みにしない。適用前に `check` で
  包含を検証する（手順 6）。
- **文字コード**：Windows 環境の Python は既定でファイルを cp932 で書くため、日本語を
  含む Markdown が UTF-8 ツールで文字化けすることがある。ファイルを書くときは
  `open(..., "w", encoding="utf-8", newline="\n")` を明示する。同梱スクリプトは読み込み
  時に UTF-8→cp932 の順でフォールバックし、書き込みは常に UTF-8 にしている。
